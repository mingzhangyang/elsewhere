# Sky Moments SM2-C — deterministic calculation snapshots

Status: computation/resource contract only. No chart renderer, Canvas/WebGL, UI, PNG, sharing, layout or SM3 work is included.

## Public API and separation of concerns

- `src/domain/skyChartSnapshot.ts`: `prepareSkyChartSnapshotInput(input)`, `assertSkyChartCatalog(catalog)`, `buildSkyChartSnapshot(input, sky, catalog?)`, and `buildPreparedSkyChartSnapshot(prepared, sky, catalog?)`. The pure builders accept canonical UTC plus an explicit location and never import upward from `lib`, fetch, or initialize resources. The third argument is a trusted catalog override for deterministic tests; omitted means the actual live `STAR_CATALOG`. `SkyChartSnapshotInput`, `SkyChartSnapshot`, `SkyChartSnapshotObject`, and `PreparedSkyChartSnapshotInput` are exported types.
- `src/services/skyChartSnapshot.ts`: `prepareSkyChartSnapshotRequest(request)` accepts either canonical UTC input or already resolved SM1 `MemorialTime`; it reuses `assertMemorialTimeConsistency` before mapping the latter to validated pure UTC domain input, retaining its exact/reference intent. `createSkyChartSnapshotCoordinator(dependencies?)` returns `generate(request, onStatus?)` and `invalidate()`. Default dependencies call `starCatalogLoaded()`, load using the existing `loadStars()`/`loadStarCatalog()` mechanism through an **on-demand dynamic import**, read the live `STAR_CATALOG`, and call `calculateSky(location, date)`. No new global state manager or explorer entrypoint import is installed. Optional dependency overrides support isolated tests.

A pure domain input has `time: { kind: 'utc', utc: '2026-06-21T16:00:00.000Z' }` **plus** an explicit `LocationInfo`. The service coordinator also accepts an already **resolved** `MemorialTime` (which includes its location), via `prepareSkyChartSnapshotRequest`. UTC strings must be canonical millisecond ISO (`Z`) instants in the existing `[1900-01-01T00:00:00.000Z, 2100-12-31T23:59:59.999Z]` inclusive range. The builder uses `validateInstant` and `validateObserver`; the memorial branch uses `assertMemorialTimeConsistency`, rather than re-resolving the civil time with the current time-zone database. The snapshot retains the `exact`/`reference`/`utc` kind, reference-time origin, saved offset and DST disambiguation, **not** the local personal event date/time text. The selected location is captured as a copy before the resource wait, including its original IANA zone; the device clock, local language, explorer camera and playback state are never consulted.

`limitingMagnitude` is optional (defaults to **6.0**) and must be finite in [-5, 20]. Snapshot objects are in the SM2-B stable order: Sun, Moon, Mercury, Venus, Mars, Jupiter, Saturn, followed by stars in codepoint ID order. Only above-horizon apparent, standard-refracted **center** altitudes (including exactly 0°) are selected. Each selected object has `id`, `kind`, `altitude`, `azimuth`, and `(x,y)` in the **SM2-A unit disc**: north up, east left. Stars include `name` (possibly empty for an unnamed HYG row), magnitude and B−V color index. Sun includes distance; Moon includes distance, phase key/angle, illuminated fraction and waxing; planets include their name, magnitude, phase and illuminated fraction, range, radius, elongation and morning/evening apparition. The explorer's `brightLimbAngle` is deliberately **not** used as the future chart-screen lunar rotation.

Only the selected objects are copied into the frozen returned snapshot. The full sky state, star field `Float32Array`, daily events, unselected stars, original catalog, camera, weather, light-pollution and rendering state are excluded. Object/array/metadata copies are frozen, but the shared HYG catalog and astronomical caches are not. Full floating-point coordinates are retained without artificial rounding.

## Lifecycle and concurrency

A coordinator call emits `loading` then resolves to one of:

| State                       | Meaning / next action                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------- |
| `ready`                     | Catalog and the full computed sky validated; usable immutable snapshot present                          |
| `error` with `input`        | Invalid UTC, saved memorial time, place or limiting magnitude; correct input                            |
| `error` with `catalog-load` | Catalog request/import failed; call `generate()` again to retry                                         |
| `error` with `catalog-data` | Loaded catalog absent, damaged or incomplete; retry may require a corrected asset or reload             |
| `error` with `calculation`  | Astronomy computation failed; diagnose the engine/environment and retry                                 |
| `error` with `snapshot`     | Computed sky incomplete, SM2-B selection failed, or SM2-A projection invalid; reject the whole snapshot |
| `stale`                     | An older request has been superseded or `invalidate()` called; never adopt its result                   |

`requestId` monotonically increases **within each coordinator**. A new `generate` call supersedes earlier calls, including when an old time/place is waiting on catalog resources. Only the most recent call invokes its final `onStatus`; older calls return `stale`. Callers should use one coordinator per active editor instance and call `invalidate()` when leaving that flow. There is no remote cancellation and no forced interruption of synchronous `calculateSky`; the result is invalidated at the async checkpoint. The existing loader's promise caching and a per-coordinator in-flight promise prevent duplicate parallel requests. A rejected promise is cleared for retry. Status messages contain stable error class names only, not original provider error strings, URLs, precise locations or personal event times.

The loader state is **not** inferred from a fabricated `starCatalogReady: true`. Before SM2-B's required flag is passed, the coordinator checks `starCatalogLoaded()`, examines the actual loaded catalog, enforces the currently generated **5,070-row HYG v4.1 derivative** for the production loader, and validates each row and its ID. It then computes with the single captured UTC instant/location. The pure builder independently requires a nonempty, structurally valid catalog, five unique complete planets, a valid Sun/Moon, every catalog star position with matching identity and photometry, and complete star-field buffers. Invalid objects are rejected even if below the horizon or fainter than the display threshold. Only a truly loaded and complete catalog with **zero above-horizon eligible stars** may produce a legitimate zero-star snapshot. These checks are intentionally stricter than the pure selector's partial-planet test contract.

`calculateSky` is the existing source of Sun, Moon, five planets, apparent-star positions and star-field buffers; `selectSkyChartObjects` (SM2-B) and `projectSkyChart` (SM2-A) are called directly, without duplicating or modifying their policies. The pure builder assumes the supplied `SkyState` was generated from exactly the same UTC instant/location: `SkyState` has no embedded provenance from which to independently re-derive this. **The coordinator enforces that pairing** by passing the captured location and `new Date(utc)` directly to `calculateSky`, then building immediately from its result. Consumers requiring this guarantee should use the coordinator, rather than pairing arbitrary stored `SkyState` objects with input themselves.

## Provenance, reproducibility and scope of scientific evidence

Snapshot `formatVersion: 1` is a schema revision. `provenance` identifies the HYG v4.1 derivative (from `scripts/import-stars.mjs` / `public/credits.html`), the **actual** catalog row count, `calculateSky / astronomy-engine`, normal standard refraction, SM2-B selection and azimuthal-equidistant projection. `catalogHash: null` explicitly states that the current lazy catalog loader exposes **no proven content hash**; the source CSV hash in the importer is **not** an installed derivative-file hash. The snapshot also does not claim an exact resolved astronomy-engine package build/version; reproducibility across installations therefore requires recording the deployment/code revision and dependency lockfile externally. For fixed installed catalog and astronomy implementation, UTC/place/options produce a stable object order and normal engine floating-point results. Byte-identical output across different engines/tzdb versions is not guaranteed.

`tests/skyChartSnapshot.test.ts` separates small synthetic policy/error/concurrency cases from **in-project** integration with the real existing HYG JSON, `loadStarCatalog`, `calculateSky`, SM2-B and SM2-A. S01/S02 remain mathematical projection tests; S03 samples actual engine-calculated near-horizon objects without establishing independent historic accuracy; S04 samples engine-calculated above-horizon **daytime** stars for New York's 2026-06-21 local noon; S05 covers Sydney and Tromsø calculated scenes. Earlier cached Horizons/USNO samples and their claims are documented in `SCIENCE.md` and existing reference tests, but **no new independent JPL/USNO astronomical positions** were obtained for the SM2-C snapshots. S06 moon crescent screen orientation and S07 broad research-grade historic accuracy remain out of scope. The existing explorer visibility and eye-safety rules remain untouched; the memorial diagram shows positions, not naked-eye visibility or safe solar observation.

Validation and build-budget results must be taken from actual `npm run validate`, `npm run format:check`, GitHub Actions and `scripts/check-build.mjs`. Because the module is not imported by an app entrypoint or explorer, its intended direct startup impact is zero; this is a design property, **not** a substitute for measuring the production output.
